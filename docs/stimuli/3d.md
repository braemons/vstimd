# 3-D shapes

Cubes, spheres and planes placed in a 3-D world and seen through a camera. They
are drawn *underneath* every 2-D stimulus in the same frame, so a fixation point,
a caption or the photodiode patch always stays on top of the 3-D scene.

```python
from vstimd import Connection
from vstimd.stimuli import (
    Color, Material3D, Plane3DParams, Shading, Sphere3DParams, Transform3D, Vec2, Vec3,
)

with Connection() as conn:
    conn.stimuli.shapes3d.create_plane(
        name="floor",
        transform=Transform3D(position_cm=Vec3(0, -15, -100)),
        params=Plane3DParams(size_cm=Vec2(160, 200)),
    )
    conn.stimuli.shapes3d.create_sphere(
        name="ball",
        transform=Transform3D(position_cm=Vec3(0, 0, -60)),
        params=Sphere3DParams(
            diameter_cm=20,
            material=Material3D(albedo=Color(0.2, 0.55, 0.9), shading=Shading.PHONG),
        ),
    )
```

`client/python/examples/scene_3d.py` animates a scene like this one, moving
objects and the camera together in deferred mode.

## World space and the camera

World space is **right-handed, Y up, in centimetres**. The camera starts at the
origin looking down **−Z** with a 60° vertical field of view, so an object at
`Vec3(0, 0, -60)` is 60 cm straight ahead and centred on screen. Up in the world
is up on screen, as it is for 2-D stimuli.

```python
from vstimd.system import Camera3D

conn.system.set_camera(Camera3D(position_cm=Vec3(0, 10, 0), yaw_deg=15, pitch_deg=-5))
```

| Field | Default | Meaning |
|---|---|---|
| `position_cm` | `(0, 0, 0)` | Where the camera is. |
| `yaw_deg` | `0` | Turn about the vertical axis. Positive turns the view **left**. |
| `pitch_deg` | `0` | Tilt. Positive looks **up**. |
| `roll_deg` | `0` | Bank about the view axis. |
| `fov_y_deg` | `60` | Vertical field of view, in (0, 180). The horizontal one follows from the display's aspect ratio. |
| `near_cm`, `far_cm` | `1`, `50000` | Nothing nearer than `near_cm` or farther than `far_cm` is drawn. |

`set_camera` replaces the whole camera. It is saved with the scene-config and,
in deferred mode, changes on the same frame as the stimuli staged with it.

### Moving the camera every frame

`set_camera` is one command per change. To travel through a scene without a
command per frame, drive the camera with an animation:

```python
nav = conn.animations.create_linear_nav_3d(20.0, wrap_period_cm=500.0)  # 20 cm/s
conn.animations.arm(nav)
...
conn.animations.set_nav_speed(nav, 40.0)                      # a scripted change
print(conn.animations.query(nav).distance_travelled_cm)      # log this
```

The camera moves along its horizontal forward direction and keeps its height.
With `wrap_period_cm`, its `z` wraps into `[0, wrap_period_cm)`: an endless
corridor is geometry that repeats with that period, which the camera circulates
through. Anything placed along it therefore repeats too — a track with unique
landmarks along its whole length is a long finite scene, not a wrapped one.

`distance_travelled_cm` is the true distance since the animation started. It never
wraps and is kept in double precision, so it is the number to record. Speed
changes with `set_nav_speed` are for a block design ("now run at 40 cm/s"), not for
streaming a treadmill's speed every frame.

The 2-D motion animations (`create_move_along_path_2d` and friends) cannot drive
the camera: they move in pixels, which mean nothing in centimetres.

## Placement: `Transform3D`

| Field | Default | Meaning |
|---|---|---|
| `position_cm` | `(0, 0, 0)` | Centre of the object. |
| `rotation_deg` | `(0, 0, 0)` | `(yaw, pitch, roll)` in degrees, applied yaw about the world's vertical axis, then pitch about the object's own X, then roll about its own Z. Positive yaw turns counter-clockwise seen from above. |
| `scale` | `(1, 1, 1)` | Multiplies the object's size per axis. Must not be negative. |

The 2-D `set_position` and `set_rotation` refuse a 3-D stimulus — pixels mean
nothing in world space. Use `conn.stimuli.shapes3d.set_transform`. `set_alpha`,
`set_enabled` and `delete` work as for any stimulus.

## Types

Sizes are **full extents**, as everywhere in vstimd: a sphere is sized by its
diameter, a cube by its side lengths.

| Type | Create with | Size |
|---|---|---|
| `Cube3D` | `create_cube(params=Cube3DParams(...))` | `size_cm: Vec3`, default `(10, 10, 10)`. `set_cube_size` changes it. |
| `Sphere3D` | `create_sphere(params=Sphere3DParams(...))` | `diameter_cm`, default `10`. `rings` / `sectors` (default 16 / 32, at most 256) set how finely it is tessellated, and are fixed at creation. `set_sphere_diameter` changes the size. |
| `Plane3D` | `create_plane(params=Plane3DParams(...))` | `size_cm: Vec2`, default `(100, 100)` — extent along X and along Z. A plane lies flat, facing up, and is visible from above only; rotate it to make a wall. `set_plane_size` changes it. |

## Appearance: `Material3D` and lighting

| Field | Default | Meaning |
|---|---|---|
| `albedo` | opaque white | The surface colour. |
| `shading` | `Shading.UNLIT` | `UNLIT` or `PHONG` — see below. |
| `emissive` | `(0, 0, 0)` | Linear RGB added after shading, for a surface that must reach a luminance whatever the light. |

**`UNLIT`** draws the albedo exactly: no lighting, no ambient term. An unlit
sphere writes the same pixel values as a 2-D circle of the same colour, which is
what most experiments want — the luminance of a stimulus does not depend on
which renderer drew it.

**`PHONG`** is lit by the scene's one directional light: diffuse shading plus a
fixed specular highlight, over an ambient term. It is not physically based.

```python
from vstimd.system import Lighting3D

conn.system.set_lighting(Lighting3D(
    ambient_color=Vec3(0.1, 0.1, 0.1),
    sun_direction=Vec3(-0.5, -1.0, -0.3),   # the direction the light travels
    sun_color=Vec3(1.0, 1.0, 1.0),
))
```

Lighting colours are linear multipliers and may exceed 1. `sun_direction` may
have any length but not zero. Like the camera, lighting is saved with the
scene-config and respects deferred mode.

## Limits

- **Translucency is unsorted.** Alpha below 1 blends, but 3-D surfaces are not
  sorted back to front, so overlapping translucent objects can look wrong.
- **No textures yet.** `texture_path` is refused.
- **No anti-aliasing.** Edges of 3-D objects are aliased.
- **Not a Raspberry Pi feature.** 3-D targets Jetson Orin and desktop GPUs. A
  display with no depth buffer format answers the create commands with
  `NotSupportedError` and keeps serving 2-D.
- **The first 3-D object may cost a frame**, while the server sets up the 3-D
  pass. Create 3-D stimuli before a trial starts, not during it.
