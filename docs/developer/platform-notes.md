# Platform Notes

## Raspberry Pi 5 (Raspbian OS)

- Networking issues (dropping connections): Energy-Efficient Ethernet flaps the Pi 5's onboard NIC. `packaging/image/build-sd-image.sh` ships a retrying udev rule plus, as the primary mechanism, an `/etc/NetworkManager/system-connections/99-disable-eee.nmconnection` keyfile (`[match] interface-name=eth*;` + `[ethtool] eee-enabled=false`) so NM disables it during its own activation state machine. An earlier version of this fix set `ethtool.eee-enabled=false` under a `NetworkManager.conf(5)` `[connection-*]` conf.d section — that mechanism only defaults a fixed whitelist of single-value properties and silently ignores the multi-value `ethtool` setting group, so it never actually applied. If EEE is still on, check first whether a real connection profile is winning over `99-disable-eee.nmconnection` (`nmcli -f GENERAL.CONNECTION device show eth0`) before reaching for a manual fix:
  ```
  sudo ethtool --set-eee eth0 eee off
  ```
- Status LED turns red after UEFI: Are you using a 27 W power supply?
- USB DisplayLink adapters (evdi) do not give deterministic frame timing — DisplayLink relays frames over USB via software encode/decode with no direct vsync from the GPU (confirmed against the kernel driver source: `evdi_enable_vblank()` is a stub, there is no periodic vblank timer at all). That rules it out for **recording sessions**, where stimulus onset must be known to the frame. It does *not* rule out stimulus presentation as such: for **behavioral training** setups, where the animal is learning a task and exact onset timing is not being measured, evdi is a perfectly usable stimulus output. Rule of thumb: fine wherever no timestamp is being trusted, unsuitable the moment one is.
  However, a compositor is **not** required to drive one — that part of the old note was wrong. evdi just needs *something* acting as DRM master pushing framebuffers to its virtual KMS device (`/dev/dri/cardN`, `driver=evdi`, separate from the real GPU node); a full desktop compositor is merely the common way to get that. vstimd has a dedicated `--evdi` backend (`server/src/render/evdi/`, see `docs/developer/evdi-direct-presentation-plan.md`) that renders through the normal Vulkan pipeline into a headless swapchain (`VK_EXT_headless_surface` — confirmed available on the V3D/Mesa driver), reads the frame back to the CPU, and presents it directly via `page_flip` + evdi's completion-event backpressure (real flow control paced to `DisplayLinkManager`'s actual USB consumption, not a synthetic clock — plain `set_crtc` every frame has no backpressure and visibly tears). Validated on this rig: real vstimd scene content renders and presents correctly, naturally paced to ~60fps by that backpressure, exercised through the full `client/python` e2e suite (126 passed, 6 pre-existing xfails). Use `--evdi` for auxiliary/status screens and for behavioral-training stimulus output; use the DRM backend for recording sessions.
- Booting straight into `--evdi` via the `vstimd.target` systemd unit: the unit's `ExecStart=` passes no render-target flag, so it needs no edits — set `backend = "evdi"` under `[display]` in the deployed rig-config (`/etc/braemons/vstimd-rig-config.toml`, default `server/config/raspberry-pi-5.toml`) instead. `--null`/`--evdi` on the command line still take priority over this if ever passed manually. With `backend` left at the default `"auto"`, this now also happens automatically on a headless boot: if no HDMI/DP display is detected but a connected DisplayLink (evdi) output is, vstimd uses it without any rig-config edit — see `detect_render_target` in `server/src/main.rs`.
- DisplayLink USB displays keep toggling on and off? Don't use a USB-C power switch
- `mesa-vulkan-drivers` is held at `25.0.7-2+rpt4+deb13u1` in `packaging/image/build-sd-image.sh`. An unheld/unpinned install pulls in whatever's current in `archive.raspberrypi.com`'s `trixie/main` suite (no backports needed — that suite itself has moved on), which broke the evdi backend's headless Vulkan swapchain (`vkCreateSwapchainKHR` → `VK_ERROR_OUT_OF_DEVICE_MEMORY`, 100% reproducible on V3D 7.1) while the DRM/HDMI path stayed unaffected. Confirmed as an upstream v3dv regression, not a vstimd or packaging bug — see the tracking issue on this repo for status and the upstream Mesa report.
  The image build asks apt for `mesa-vulkan-drivers=25.0.7-2+rpt4+deb13u1` by name, which resolves from whichever configured source actually has it — normally the `braemons/packages` archive (already trusted on every image for in-place updates), which vendors this exact version into every suite's pool (see [`pinned-packages.txt`](https://github.com/braemons/packages/blob/main/pinned-packages.txt) there) precisely so this doesn't depend on `archive.raspberrypi.com` keeping the old build around. If that archive doesn't have the pin yet (or apt updates are disabled on this image), the script falls back to curling the `.deb` straight from `archive.raspberrypi.com`'s pool — old pool files survive there after the Packages index rotates past them, but that's not a guarantee, just an observation. Either way it's installed with `apt-mark hold` so a later `apt-get install -y -f`, or a deployed rig's own `apt upgrade`, can't pull 26.x back in.
  Two earlier versions of this fix didn't actually work: an `/etc/apt/preferences.d` version pin (`Pin: version 25.0.7-2+rpt4*`, `Pin-Priority: 1001`) stopped working once that version aged out of the repo's published Packages index entirely (apt can't pin what has no candidate, so it silently fell through to whatever *was* available), and a same-repo `dpkg -i` direct from the pool worked but left every future image build dependent on that pool file staying reachable forever. Don't remove the hold until the v3dv regression is confirmed fixed upstream and the fix has made it into a `+rpt` build.
