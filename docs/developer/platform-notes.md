# Platform Notes

## Raspberry Pi 5 (Raspbian OS)

- Networking issues (dropping connections)
  ```
  sudo ethtool --set-eee eth0 eee off
  ```
- Status LED turns red after UEFI: Are you using a 27 W power supply?
- USB DisplayLink adapters (evdi) do not give deterministic frame timing — DisplayLink relays frames over USB via software encode/decode with no direct vsync from the GPU (confirmed against the kernel driver source: `evdi_enable_vblank()` is a stub, there is no periodic vblank timer at all). That rules it out for **recording sessions**, where stimulus onset must be known to the frame. It does *not* rule out stimulus presentation as such: for **behavioral training** setups, where the animal is learning a task and exact onset timing is not being measured, evdi is a perfectly usable stimulus output. Rule of thumb: fine wherever no timestamp is being trusted, unsuitable the moment one is.
  However, a compositor is **not** required to drive one — that part of the old note was wrong. evdi just needs *something* acting as DRM master pushing framebuffers to its virtual KMS device (`/dev/dri/cardN`, `driver=evdi`, separate from the real GPU node); a full desktop compositor is merely the common way to get that. vstimd has a dedicated `--evdi` backend (`server/src/render/evdi/`, see `docs/developer/evdi-direct-presentation-plan.md`) that renders through the normal Vulkan pipeline into a headless swapchain (`VK_EXT_headless_surface` — confirmed available on the V3D/Mesa driver), reads the frame back to the CPU, and presents it directly via `page_flip` + evdi's completion-event backpressure (real flow control paced to `DisplayLinkManager`'s actual USB consumption, not a synthetic clock — plain `set_crtc` every frame has no backpressure and visibly tears). Validated on this rig: real vstimd scene content renders and presents correctly, naturally paced to ~60fps by that backpressure, exercised through the full `client/python` e2e suite (126 passed, 6 pre-existing xfails). Use `--evdi` for auxiliary/status screens and for behavioral-training stimulus output; use the DRM backend for recording sessions.
- Booting straight into `--evdi` via the `vstimd.target` systemd unit: the unit's `ExecStart=` passes no render-target flag, so it needs no edits — set `backend = "evdi"` under `[display]` in the deployed rig-config (`/etc/braemons/vstimd-rig-config.toml`, default `server/config/raspberry-pi-5.toml`) instead. `--null`/`--evdi` on the command line still take priority over this if ever passed manually. With `backend` left at the default `"auto"`, this now also happens automatically on a headless boot: if no HDMI/DP display is detected but a connected DisplayLink (evdi) output is, vstimd uses it without any rig-config edit — see `detect_render_target` in `server/src/main.rs`.
- DisplayLink USB displays keep toggling on and off? Don't use a USB-C power switch
- `mesa-vulkan-drivers` (and the rest of the mesa source package: `mesa-libgallium`, `libegl-mesa0`, `libgl1-mesa-dri`, `libglx-mesa0`, `mesa-va-drivers`, `mesa-vdpau-drivers`) is pinned to `25.0.7-2+rpt4*` in `packaging/image/build-sd-image.sh`. Without the pin, an unpinned `apt-get install -y -f` can pull in whatever's highest-priority across the enabled repos — RaspiOS images have `trixie-backports` enabled by default alongside `archive.raspberrypi.com`, and backport version strings normally outrank the plain-archive ones. That's how a build picked up `26.2.0-1~bpo13+0~rpt2` and broke the evdi backend's headless Vulkan swapchain (`vkCreateSwapchainKHR` → `VK_ERROR_OUT_OF_DEVICE_MEMORY`, 100% reproducible on V3D 7.1) while the DRM/HDMI path stayed unaffected. Confirmed as an upstream v3dv regression, not a vstimd or packaging bug — see the tracking issue on this repo for status and the upstream Mesa report. Don't remove the pin until that's confirmed fixed upstream and the fix has made it into a `+rpt` build.
